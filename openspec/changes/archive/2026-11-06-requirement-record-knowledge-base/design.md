# 设计说明

## 1. 背景与约束

本次变更围绕需求实体补齐档案、详情与知识库，把技能包加载固化为可自检能力，并把需求状态扩展为覆盖调研到全国推广的 14 阶段主线。设计遵循以下既有约束：

- 提案确认闸门与角色权限模型不变；状态机由混合命名的 12 个状态调整为 14 阶段主线加 3 个非阶段状态，门禁随阶段重排。
- 所有受控写入服务端校验权限并记录审计；批量操作逐条留痕并生成批次号。
- 需求编号只进入追踪表、契约、标记与附录索引，不进入正文叙述。
- 产物预览必须自包含，不引用外部图床、CDN 或外部样式。
- 技能包只读取元数据、契约、提示词与模板，不执行包内脚本。

## 2. 数据模型

### 2.1 需求档案

`requirements` 表新增两列，均为可空，历史数据不做破坏性回填：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `description` | TEXT | 需求说明。为空时读取澄清描述，再回退原文摘要；编辑后独立保存 |
| `leads_json` | TEXT | `{ tech, test, implementation }` 三个负责人姓名，空字符串表示未指定 |

复用既有字段：

| 业务字段 | 存储 |
| --- | --- |
| 需求名称 | `title` |
| 提交人 | `requester_json.name` |
| 提交组织 | `requester_json.enterprise` / `requester_json.department` |
| 提交时间 | `source_json.submittedAt` 优先，缺失回退 `created_at` |
| 需求状态 | `status` |
| 所属迭代 | `iteration_id` |
| 优先级 | `priority_json.grade` |
| 产品经理 | `milestones_json.productManager` |
| 负责人 | `owner_id` |

### 2.2 应用功能点

`involved_apps_json` 由 `[{ name, kind }]` 扩展为：

```json
[
  {
    "name": "应用名称",
    "kind": "internal",
    "functions": [
      { "id": "FUNC-...", "name": "功能点名称", "description": "功能点说明" }
    ]
  }
]
```

- 读取时缺失 `functions` 统一归一化为空数组，不批量改写历史 JSON。
- 功能点新增时生成稳定 `id`；名称在同一应用内去重；应用名称必须落在项目应用范围或既有涉及应用内。
- 功能点随应用一起写入 `involved_apps_json`，不单独建表：功能点始终从属于应用，读取与详情聚合都按应用分组，避免引入额外关联表与迁移。

### 2.3 里程碑

`milestones_json` 扩展为：

```json
{
  "productManager": "",
  "reviewedAt": "",
  "submittedAt": "",
  "testedAt": "",
  "uatAt": "",
  "pilotAt": "",
  "releasedAt": "",
  "plan": {},
  "history": []
}
```

- `submittedAt` 字段键保持不变，显示名由「开发提测时间」改为「开发完成时间」，作为进入「待测试验证」的回填节点。
- 新增 `pilotAt`（试点完成时间），作为进入「待上线发版」的回填节点。
- 顺序为评审完成 → 开发完成 → 测试完成 → UAT → 试点 → 上线推广，实际时间与计划时间分别校验。
- 六个完成时间与阶段的对应、自动回填与回退清除规则见第 3 节；既有手动编辑与审计规则不变。
- `history` 保留字段级变更记录，新增试点节点同样写入。

### 2.4 产物更新时间

`prototypes`、`specs`、`iteration_specs` 各新增 `updated_at` 列：

- 新建时与 `created_at` 相同。
- 原型确认/修订、说明书发布/状态变更、迭代说明书状态变更时更新。
- 历史记录该列为空时，知识库与详情回退使用 `created_at`。

### 2.5 批次记录

`batch_operations` 新增：

| 列 | 说明 |
| --- | --- |
| `kind` | `status` 或 `progress`，历史记录回填为 `status` |
| `changes_json` | 进展维护的目标字段与值，状态批次为空对象 |

`target_status` 在进展维护批次中保存空字符串。

### 2.6 技能包

不新增技能包表，使用代码内固定清单 `BUILTIN_SKILL_PACK` 描述技能包名称、版本与 13 个技能的标准映射。技能包本体作为 `skills` 表中的内置记录；项目可见性继续由 `project_skills` 绑定表表达。

标准映射：

| 技能 | 工作台环节 | 说明 |
| --- | --- | --- |
| prd-pipeline | 全部（空数组） | 编排技能，不绑定单一环节，由模型按上下文判断 |
| prd-profile | clarify | 项目画像 |
| prd-discovery | clarify | 需求澄清 |
| grill-me | clarify | 追问 |
| grilling | clarify | 追问 |
| prd-context | analysis | 前置上下文 |
| prd-design-spec | analysis、prototype | 设计规范 |
| prd-analysis | analysis | 结构化分析 |
| prd-visuals | analysis、prototype | 图表 |
| prd-prototype | prototype | 界面原型 |
| archify | analysis、prototype | 架构与流程图 |
| prd-assemble | spec | 说明书组装 |
| prd-quality | review | 全链路质检 |

## 3. 状态模型

需求状态由 14 个编号阶段组成主线，另保留已关闭、挂起、已丢弃三个非阶段状态。状态值使用「序号-名称」的完整字符串参与展示，存储值只保存名称，避免序号变更时批量改库。

### 3.1 状态清单

| 序号 | 状态 | 语义 | 进入条件 | 工作台环节 |
| --- | --- | --- | --- | --- |
| 0 | 需求调研中 | 已登记待调研，尚未确认 | 需求登记或确认退回 | clarify |
| 1 | 待需求分析 | 已确认并分配编号，尚未开始分析 | 确认清单通过 | analysis |
| 2 | 需求分析中 | 结构化分析、原型与说明书编写 | 从待需求分析开始 | analysis |
| 3 | 需求评审中 | 待评审、评审进行与建议闭环 | 原型已确认且说明书已发布 | review |
| 4 | 待开发 | 评审通过，等待进入开发 | 评审通过且建议全部关闭 | change |
| 5 | 开发中 | 开发实施 | 技术负责人已指定 | change |
| 6 | 待测试验证 | 开发完成，等待测试 | 测试负责人已指定 | change |
| 7 | 测试验证中 | 测试执行 | 从待测试验证开始 | change |
| 8 | 待UAT | 测试完成，等待用户验收 | 测试完成时间已回填 | change |
| 9 | UAT中 | 用户验收测试 | 从待UAT开始 | change |
| 10 | 待试点 | UAT 完成，等待试点 | 实施负责人已指定 | change |
| 11 | 试点中 | 试点运行 | 从待试点开始 | change |
| 12 | 待上线发版 | 试点完成，纳入发版计划 | 试点完成时间已回填 | change |
| 13 | 全国推广中 | 已发版，进入推广 | 上线推广时间已回填 | change |

### 3.3 状态与里程碑联动

| 阶段动作 | 回填字段 | 显示名 |
| --- | --- | --- |
| 需求评审中 → 待开发 | `reviewedAt` | 评审完成 |
| 开发中 → 待测试验证 | `submittedAt` | 开发完成 |
| 测试验证中 → 待UAT | `testedAt` | 测试完成 |
| UAT中 → 待试点 | `uatAt` | UAT 完成 |
| 试点中 → 待上线发版 | `pilotAt` | 试点完成 |
| 待上线发版 → 全国推广中 | `releasedAt` | 上线推广 |

- 回填只在字段为空时写入；已有值不覆盖，人工修正优先。
- 回退跨越某个完成节点时，清除该节点及之后由系统自动回填的日期；人工登记的日期保留并在详情与跟进视图标记「待复核」。
- 清除与保留都写入里程碑 `history` 与状态事件，事件中记录来源阶段与目标阶段。
- 顺序校验在回填后执行；若人工登记的保留日期与当前阶段冲突，阻断下一次保存并要求先修正。

### 3.4 展示与统计

- 所有状态出现的位置统一展示「序号-名称」，例如 `2-需求分析中`；已关闭、挂起、已丢弃只显示名称。
- 状态筛选、批量维护目标、导出与通知使用同一份状态字典，顺序固定为 0 至 13，异常状态排在最后。
- 状态分布按序号升序分组，同时给出数量与占比；挂起单列，已丢弃不计入分布。
- 完成率按「（全国推广中 + 已关闭）/ 参与统计需求数」计算；迭代完成口径为迭代已发布且全部需求处于全国推广中或已关闭。
- 历史记录中的旧状态名称按原文展示，并追加「历史状态」标记，不做二次改写。

### 3.5 存量迁移

| 旧状态 | 新状态 |
| --- | --- |
| 待澄清 | 需求调研中 |
| 已确认 | 待需求分析 |
| 分析中 | 需求分析中 |
| 原型中 | 需求分析中 |
| 待评审 | 需求评审中 |
| 评审中 | 需求评审中 |
| 开发中 | 开发中 |
| 待验收 | 待测试验证 |
| 已上线 | 全国推广中 |
| 已关闭 | 已关闭 |
| 挂起 | 挂起，`suspended_from` 同步映射 |
| 已丢弃 | 已丢弃 |

- 迁移只匹配旧名称，重复执行不产生变化；已是新名称的记录跳过。
- 每条被迁移需求写入一条 `status-migration` 事件，记录旧状态、新状态、迁移批次与时间，操作人记为系统。
- `stall_since` 重置为迁移时间，避免迁移后立即产生停滞预警。
- 历史状态事件、批次记录与导出记录保留旧名称；批次列表遇到旧名称时展示「历史状态：待验收」。
- 迁移前校验状态字典与代码内 `STATES` 一致，不一致时中止并输出差异。

### 3.6 工作台环节映射

| 当前状态 | 工作台环节 |
| --- | --- |
| 需求调研中 | clarify |
| 待需求分析、需求分析中 | analysis |
| 需求评审中 | review |
| 待开发至全国推广中 | change |
| 已关闭、已丢弃 | change，只读提示 |
| 挂起 | 按 `suspended_from` 映射，缺失时回退 change |

- 需求详情「进入工作台」、需求池「打开」与通知跳转共用该映射。
- 分析环节内的原型与说明书入口仍由工作台页签提供，映射只决定默认落点。

### 3.7 迭代发布联动

- 发布门禁：迭代内全部需求状态属于「待上线发版、全国推广中、已关闭」，存在其它状态时列出未通过项。
- 发布执行：对待上线发版需求逐条执行「待上线发版 → 全国推广中」，回填上线推广时间；全国推广中与已关闭保持原状。
- 发布写入状态批次，`source` 为 `iteration-release`；逐条写审计与状态事件。
- 发布后迭代进入只读，拒绝新增排期、状态推进与进展维护；已发布迭代中的需求仍可查看与导出。
- 发布过程中任一条失败时整批回滚，迭代保持未发布并返回失败清单。

## 4. 接口设计

### 4.1 需求档案与进展

| 方法 | 路径 | 作用 | 权限 |
| --- | --- | --- | --- |
| PATCH | `/api/requirements/:id/profile` | 保存需求说明、负责人、应用与功能点 | `requirement.clarify` |
| PATCH | `/api/requirements/:id/milestones` | 保存里程碑（扩展现有接口） | `milestone.edit` |
| POST | `/api/projects/:projectId/requirements/batch-progress` | 多条或迭代范围统一维护进展 | `batch.status` 或 `milestone.edit` |
| GET | `/api/projects/:projectId/requirements/batch-progress/preview` | 预览目标范围与逐条校验结果 | 项目成员 |

`PATCH /profile` 请求体：

```json
{
  "description": "需求说明",
  "leads": { "tech": "姓名", "test": "姓名", "implementation": "姓名" },
  "apps": [
    { "name": "应用名称", "kind": "internal", "functions": [{ "id": "FUNC-1", "name": "功能点", "description": "说明" }] }
  ]
}
```

字段均可选；传 `apps` 时整体替换应用清单与功能点。所有变更写审计与事件，前后值完整保留。

`POST /batch-progress` 请求体：

```json
{
  "requirementIds": ["..."],
  "iterationId": "...",
  "filter": { "status": "开发中" },
  "statusTo": "待测试验证",
  "effectiveAt": "2026-11-06T10:00:00.000Z",
  "milestones": { "pilotAt": "2026-11-05" },
  "leads": { "test": "姓名" }
}
```

- `requirementIds` 与 `iterationId` 二选一；`iterationId` 下可用 `filter` 缩小范围。
- 迭代范围固定排除「需求调研中」与「已丢弃」。
- 状态推进复用 `transitionRequirement` 与门禁；里程碑复用 `applyMilestones`；负责人复用档案校验。
- 单条校验失败进入失败清单，其余继续执行；任一目标需求无权限时整批返回 403，且不写入任何记录。
- 已发布迭代内的需求拒绝状态与里程碑变更，失败项给出迭代原因。
- 每条成功项写独立审计与事件；批次汇总写入 `batch_operations`，返回批次号、成功清单与失败清单。

### 4.2 需求详情

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/requirements/:id/overview` | 返回基本信息、过程文档与进展聚合 |

响应结构：

```json
{
  "requirement": { "id": "", "code": "", "title": "", "status": "", "description": "" },
  "basic": { "requester": {}, "submittedAt": "", "apps": [], "leads": {}, "iteration": {}, "priority": {}, "owner": {}, "milestones": {} },
  "documents": {
    "specs": [],
    "flows": [],
    "prototypes": [],
    "outputs": []
  },
  "progress": {
    "nextMilestone": {},
    "milestones": [],
    "timeline": [],
    "batches": [],
    "gates": []
  },
  "permissions": { "canEdit": false, "canAdvance": false, "canExport": false }
}
```

- 一次请求完成聚合，产物列表只取必要字段，不返回 HTML 正文。
- 过程文档按版本倒序；流程图来自存在功能流程步骤的分析版本；输出物汇总需求说明书 Word/HTML、关联迭代说明书版本与导出记录。
- 访客仅返回已发布说明书与已确认原型，草稿产物不出现。
- 详情页只做汇总与档案/进展维护，不承载会话与环节生产。

### 4.3 知识库

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/projects/:projectId/knowledge` | 分页查询三类产物 |
| GET | `/api/requirements/:id/analysis-versions/:version/flow-preview` | 流程图自包含预览 |

查询参数：`type`（flowchart/prototype/spec）、`q`、`iterationId`、`manager`、`from`、`to`、`page`、`pageSize`。`pageSize` 上限 100，默认 20。

统一 DTO：

```json
{
  "id": "flow:REQ-1:3",
  "type": "flowchart",
  "title": "需求标题 · 功能流程",
  "version": 3,
  "status": "analysis",
  "requirement": { "id": "", "code": "", "title": "" },
  "iteration": { "id": "", "name": "" },
  "productManager": "姓名",
  "createdAt": "",
  "updatedAt": "",
  "previewUrl": "/api/requirements/REQ-1/analysis-versions/3/flow-preview",
  "downloadUrl": null,
  "meta": { "stepCount": 5, "pageCount": null }
}
```

- 知识库在读取时聚合，不新增索引表；产物创建、更新、删除后列表自然一致。
- 流程图产物单元为一个分析版本；流程步骤为空的分析版本不进入知识库，但在需求详情中显示空态。
- 需求说明书包含需求级说明书与迭代级说明书；迭代级说明书的 `requirement` 为空，`meta.requirementCount` 记录纳入需求数。
- 产品经理优先取需求里程碑中的产品经理；缺失时回退产物创建人；迭代级说明书取生成人。
- 预览复用既有说明书与原型预览地址；流程图预览由服务端生成自包含 HTML，内联 SVG 或纯 CSS 绘制，文本全部转义。
- 访客过滤规则与详情一致。

## 5. 详情页与入口

### 5.1 路由

- 需求详情：`#/p/:projectId/requirements/:id`
- 知识库：`#/p/:projectId/knowledge`

路由放在工作台路由 `#/p/:projectId/req/:id/:stage` 之外，避免与环节参数冲突。直接访问、刷新与返回列表都使用同一路由。

### 5.2 入口

- 需求池：需求编号与标题可点击进入详情；新增「查看详情」按钮；保留「打开」进入当前环节工作台。
- 迭代详情：需求编号与标题可点击进入详情；新增「查看详情」；保留「打开」进入工作台。
- 详情页头部提供「进入工作台」，按当前状态映射到对应环节。
- 详情页头部提供「维护进展」，打开单条进展维护面板。

### 5.3 页面结构

1. **概要头**：编号、标题、状态与阶段步骤、所属迭代、优先级、产品经理、最近里程碑与操作按钮。
2. **基本信息**：需求说明、提交信息、关联应用与功能点、负责人、里程碑与计划。
3. **过程文档**：结构化说明书、流程图、原型、输出物四个分组，按版本倒序，支持预览与下载。
4. **进展**：状态时间线、里程碑完成度、门禁校验、相关批次记录。

编辑能力按 `permissions` 控制；只读角色隐藏编辑入口，服务端仍二次校验。

## 6. 技能包加载与自检

### 6.1 注册

- `BUILTIN_SKILL_PACK` 固定声明技能包名称、版本与 13 个技能的标准 slug、名称、版本、说明与环节映射。
- 服务启动调用 `ensureBuiltinSkills` 幂等注册：缺失则插入，内置记录的名称、说明、环节与模板按标准值校准；用户导入的同名技能不覆盖。
- `ensureBuiltinBindings` 为新项目与存量项目补齐绑定；已存在的绑定保留用户自定义的环节与启停状态。
- 技能包技能只登记元数据与契约，不读取或执行包内脚本。
- 存量演示技能（澄清追问、结构化分析、界面原型、评审归并）继续保留在技能列表中，但不属于技能包，不计入覆盖数量，并在覆盖报告中单列为「非技能包技能」。

### 6.2 覆盖自检

`GET /api/projects/:projectId/skills/pack` 返回：

```json
{
  "pack": { "name": "qoder-prd-skill-pack", "version": "1.3.1", "expected": 13 },
  "summary": { "loaded": 13, "bound": 13, "compliant": 13, "issues": 0 },
  "skills": [
    {
      "slug": "prd-analysis",
      "expectedStages": ["analysis"],
      "packageStatus": "loaded",
      "bindingStatus": "bound",
      "actualStages": ["analysis"],
      "enabled": true,
      "issues": []
    }
  ]
}
```

`packageStatus`：`loaded` / `missing` / `version-mismatch`。
`bindingStatus`：`bound` / `unbound` / `disabled` / `stage-mismatch`。

### 6.3 补齐

`POST /api/projects/:projectId/skills/pack/repair`：

- 权限：项目管理员或产品经理且具备技能管理权限。
- 默认只补齐缺失技能、缺失绑定与停用绑定，不覆盖用户已自定义的环节。
- 请求显式携带 `resetStages: true` 时，才把环节恢复为标准映射。
- 返回补齐前后对照；写入审计，记录操作人、项目、技能包版本与逐项变化。
- 非管理角色只读查看覆盖报告，不提供补齐入口。

### 6.4 说明书技能迁移

- 内置说明书技能由 `spec-assemble@1.0.0` 迁移为 `prd-assemble@1.3.1`，继续使用平台维护的文档模板、占位符与校验规则。
- 迁移时把指向 `spec-assemble` 的项目绑定改指向 `prd-assemble`，保留启用状态与自定义环节。
- 历史迭代说明书保留原 `skill_slug` 与 `skill_version`，不追改；重新生成时默认沿用上一版本技能，若该技能已停用则按现有规则要求重新选择。
- 文档技能解析优先级调整为：显式选择 → 上一版本可用技能 → 内置 `prd-assemble` → 项目内唯一可用文档技能。

## 7. 备选方案与取舍

| 决策 | 备选 | 选择理由 |
| --- | --- | --- |
| 采用 14 阶段编号主线 | 保留现有混合状态并按需增加节点 | 现有状态只到「已上线」，无法表达测试验证、UAT、试点与全国推广；编号主线可直接用于展示、统计与门禁 |
| 状态值只存名称，序号由字典拼接展示 | 存储「0-需求调研中」完整字符串 | 序号或文案调整时无需批量改库；历史记录与筛选口径更稳定 |
| 合并待评审与评审中为需求评审中 | 保留两个状态并新增阶段序号 | 阶段清单只定义单一需求评审中；评审轮次、任务与建议已能表达评审批次 |
| 回退清除自动回填日期 | 回退保留全部完成日期 | 保留会与当前阶段矛盾，导致顺序校验与完成率失真；自动回填可重建，人工日期保留并标记待复核 |
| 迭代发布时批量推进待上线发版 | 保持发布只改迭代状态 | 发布门禁已要求全部需求完成，发布动作与需求状态应一致，否则迭代已发布但需求仍停留待上线发版 |
| 知识库读取时聚合 | 新建 `knowledge_artifacts` 索引表 | 产物已分散在既有表，索引表需要双写与回填，易与真实状态不一致；当前数据量下读取聚合更可靠 |
| 功能点存入 `involved_apps_json` | 新建应用功能点表 | 功能点始终从属应用，JSON 与现有模型一致；避免额外关联表与迁移，详情一次读取 |
| 里程碑键 `submittedAt` 保持不变 | 新增 `developedAt` 并保留提测 | 提测与开发完成在当前流程中同一节点，新增字段会造成两个近似日期与门禁歧义 |
| 技能映射到六个工作台环节 | 引入技能包的九个流水线阶段 | 工作台环节是既有事实；引入新阶段会扩散到权限、会话与界面，映射到六环节即可满足按环节使用 |
| 迁移内置说明书技能到 `prd-assemble` | 同时保留 `spec-assemble` | 双内置文档技能会造成候选歧义；迁移绑定并保留历史记录可兼顾一致性与追溯 |

## 8. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 状态迁移覆盖不全，历史需求停留在旧名称 | 启动时执行幂等迁移；迁移前列出将变更记录数；遇到未知状态中止并输出差异；统计只读取新状态 |
| 阶段增多造成入口拥挤与误操作 | 列表与详情只展示当前状态允许的下一步；批量维护只列出可达目标；非法跳转由服务端拒绝 |
| 迭代发布批量推进部分失败 | 发布在单事务内执行，任一条失败整批回滚，迭代保持未发布并返回失败清单 |
| 旧批次与事件中的旧状态造成统计混淆 | 统计只基于需求当前状态；历史记录标记「历史状态」，不参与分布与完成率 |
| 自动回填与人工登记日期冲突 | 人工优先且回填不覆盖；回退只清除自动值；冲突时阻断下一步保存并要求先修正 |
| 历史应用 JSON 缺少功能点，编辑时整体替换造成丢失 | 读取统一归一化；保存前以服务端当前应用清单为基线合并，未提交的应用保留原功能点 |
| 批量进展部分失败造成口径争议 | 返回逐条成功/失败与原因；失败项不写入；批次记录完整保留 |
| 已发布迭代内需求被批量修改 | 复用现有已发布迭代只读规则，逐条拒绝并说明 |
| 知识库聚合查询随数据量增长变慢 | 按项目与类型加索引；分页上限 100；仅查询必要列；流程图按版本懒加载预览 |
| 技能包版本升级覆盖用户自定义 | 内置注册只校准元数据与模板，绑定环节与启停保留；升级需显式迁移 |
| 流程图渲染引入 XSS | 所有流程文本转义；预览响应使用 `text/html`、`nosniff` 与严格 CSP；不拼接未转义 JSON |
| 详情聚合返回过多数据 | 只返回摘要与预览地址，不返回 HTML/Word 正文；文档与时间线分页或限量 |

## 9. 测试计划

- **场景测试**：档案字段读写、应用功能点增删改与重复校验、负责人校验、单条里程碑顺序冲突、批量进展全部成功/部分失败/权限整批拒绝/迭代范围/已发布迭代、详情聚合与访客过滤、知识库三类查询与筛选分页、流程图预览与空流程、技能包覆盖与补齐、说明书技能迁移与历史追溯。
- **状态测试**：14 阶段合法流转与非法跳转、各阶段门禁（评审通过、负责人缺失）、六个完成时间自动回填、回退清除与人工日期保留、挂起与恢复、状态展示序号、筛选与分布统计、迁移幂等与历史保留、迭代发布批量推进与失败回滚、工作台环节映射。
- **权限测试**：产品经理、管理员、评审人、开发人员、访客分别访问详情、知识库、批量进展与技能包补齐；开发人员执行提测与测试通过，产品经理执行 UAT、试点与发版。
- **构建验证**：类型检查、生产构建、全量场景测试。
- **浏览器走查**：需求池与迭代详情两个详情入口、详情四个区块、知识库三类列表与预览、批量维护进展、状态步骤展示与推进、设置页技能包覆盖报告与补齐。
