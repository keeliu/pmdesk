# 产品经理需求管理工作台

## 项目背景

产品经理的需求管理被拆散在聊天、会议纪要、文档、表格与设计工具之间：需求来源分散、分析靠个人经验、评审材料手工拼装、原型依赖设计排期、状态靠人肉同步、排期靠估算。

同时，AI 大多以聊天窗口的形式存在，能产出不错的内容，但结果停留在对话里，无法成为可校验、可流转、可追溯的工程资产。

本项目要建设一个以自然语言为入口、由技能编排、用代码保障确定性的需求管理工作台，让产品经理在同一处完成从需求收集到开发跟进的全过程。

## 项目目标

- 需求从登记到形成可开发需求包的中位耗时降到 4 小时以内。
- 需求关键字段完整度达到 90% 以上。
- 评审一次通过率达到 70% 以上。
- AI 提案一次采纳率达到 60% 以上。
- 改进建议闭环率达到 100%。

## 目标用户

| 角色 | 职责 |
| --- | --- |
| 产品经理 | 需求全流程负责人，唯一可确认需求与关闭改进建议的角色 |
| 产品负责人 | 评审签署与项目级设置 |
| 研发负责人 | 技术评审、容量评估与排期 |
| 测试负责人 | 验收标准与验收 |
| 业务方 | 提交需求、查看进度 |
| 管理员 | 项目、成员、模型与技能配置，例外豁免 |

## 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 交付形态 | Qoder Sites 云端站点 | 单一 Web 工作台，不做多租户 |
| 前端 | React + TypeScript | 桌面浏览器优先，响应式布局 |
| 后端 | Serverless Functions (Node.js) | 状态机、门禁、权限、导出均在服务端执行 |
| 数据 | 平台托管数据库 | 需求、产物、版本、事件 |
| 文件 | 对象存储 | 原始素材、原型 HTML、截图、导出文档 |
| 模型 | OpenAI 兼容网关 | 支持用户自带 Key，按能力路由 |
| 导出 | 服务端渲染 | 自包含 HTML 与 Word |

## 架构约束

1. 前端不直连模型服务，所有调用经统一网关。
2. 模型只产出提案，写入事实前必须经过确认；模型无权执行高风险动作。
3. 状态机、门禁、编号分配、优先级计算、依赖检测在服务端以代码实现，模型不参与。
4. 事件日志只追加不修改，是审计与统计的唯一事实来源。
5. 分析、说明书、原型均为只读预览，修改只能通过会话发起。
6. 分享与导出均需经过权限校验并写入审计日志。

## 领域术语

| 术语 | 含义 |
| --- | --- |
| 待澄清箱 | 尚未被产品经理确认的需求集合，无编号，不可排期 |
| 需求池 | 已完成确认并分配唯一编号的需求集合 |
| 需求编号 | `REQ-<项目号>-<流水号>`，确认时分配且唯一 |
| 环节 | 工作台的视图分组：澄清、分析、原型、评审、调整；不等于需求状态 |
| 需求状态 | 由状态机维护的 14 阶段主线：需求调研中、待需求分析、需求分析中、需求评审中、待开发、开发中、待测试验证、测试验证中、待UAT、UAT中、待试点、试点中、待上线发版、全国推广中；另有已关闭、挂起、已丢弃三个非阶段状态 |
| 阶段序号 | 需求状态的 0 至 13 编号，界面以「序号-名称」展示，存储只保留名称 |
| 需求分析说明书 | 一需求一份、可由分析版本与原型版本自动组装的正式文档 |
| 改进建议 | 评审意见归并后的可闭环条目，带编号、严重程度、责任人与状态 |
| 技能包 | 提示词模板 + 输入契约 + 输出结构 + 产物模板 + 校验规则的集合 |
| 提案 | 模型生成的待确认变更，确认后才写入数据库 |

## 开发约定

- 界面语言为中文，日期格式为 `YYYY-MM-DD`，时区为 `Asia/Shanghai`。
- API 统一返回 JSON，错误包含稳定的错误码与可读消息。
- 需求编号只允许在确认时分配，任何其他路径不得生成编号。
- 所有列表接口支持分页，默认每页 20 条，上限 100 条。
- 所有写操作记录操作人、时间、前后状态与来源。
- 不引入多租户、计费与移动端原生应用。
