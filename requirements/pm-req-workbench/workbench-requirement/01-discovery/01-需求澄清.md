## 2. 已掌握的信息

- 使用者是产品经理，核心诉求是用自然语言完成需求管理的全流程，减少工具切换与手工整理。
- 首版形态为 Qoder Sites 云端站点，单一 Web 工作台，不做多租户、代码托管、工时甘特、移动端 App 与商业化计费。
- AI 能力采用混合模式：统一模型网关支持用户自带 Key，关键环节以技能包执行。
- 工作台沿用既有 prd-* 技能的方法论与产物体系，作为其可视化外壳，不另造一套方法论。
- 已有初版产品需求分析文档，本次补充八条流程性要求，需要整体收敛。

## 3. 需求澄清单

### 3.1 需求描述

| 项目 | 内容 |
| --- | --- |
| 需求名称 | 产品经理通过自然语言完成需求从收集到开发跟进的端到端管理，以减少工具切换与手工产物整理 |
| 系统范围 | 平台：需求管理工作台；应用：需求工作台 Web 端；模块：收集与澄清、确认与需求池、需求分析、原型 DEMO、说明书与需求清单、需求评审、开发期变更管理、状态跟进与迭代规划、模型与技能管理 |
| 统建/个性化 | 统建，单产品团队内部使用，不涉及多单位差异 |
| 企业范围 | 产品团队（1 个），无个性化单位 |
| 前置条件 | 项目画像已确认；模型网关可用；用户具备产品经理角色 |
| 最终产出 | 需求清单、需求分析说明书（HTML 在线预览与 Word 导出）、可交互原型、评审记录与改进建议清单 |

### 3.2 流程图

| 节点 | 角色/岗位 | 动作 | 分支条件 | 分支结果 | 下一节点 |
| --- | --- | --- | --- | --- | --- |
| 收集 | 产品经理 / 业务方 | 粘贴文本、上传文件、表单提交或对话登记 | 材料含多条诉求 | 自动拆分为多条待澄清需求 | 待澄清 |
| 待澄清 | 产品经理 | 补齐角色、目标、范围、边界、验收，初判涉及应用 | 信息齐备 | 进入确认环节 | 确认 |
| 确认 | 产品经理 | 审阅并确认澄清单 | 通过 | 分配唯一编号，进入需求池 | 分析 |
|  |  |  | 不通过 | 退回待澄清，不分配编号 | 待澄清 |
| 分析 | 产品经理 | 会话式开展分析，右屏结构化预览 | 分析完成 | 更新需求清单与说明书草稿 | 原型 |
| 原型 | 产品经理 | 预览交互、提出优化、确认无误 | 确认 | 原型写入说明书 | 评审 |
| 评审 | 评审人 / 产品经理 | 在线预览说明书与原型，记录意见 | 通过且建议全部闭环 | 进入开发 | 开发 |
|  |  |  | 未通过 | 退回分析完善 | 分析 |
| 开发 | 产品经理 / 研发 | 开发期细化需求 | 影响小 | 直接更新并留版本 | 开发 |
|  |  |  | 影响大 | 重新登记新需求或重新评审 | 确认 / 评审 |

最终结果输出：一份可导出的需求清单、每条需求一份需求分析说明书、与说明书一致的可交互原型、可通过门禁的需求状态。

### 3.3 需求说明（逐步拆解）

| 步骤 | 节点 | 角色/岗位 | 输入 | 约束条件 | 处理逻辑 | 输出 | 异常/分支 | 本步完成标准 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| S1 | 收集与澄清 | 产品经理 | 任意形态的需求材料 | 未确认需求不分配编号 | 抽取结构化字段，生成澄清问题，初判涉及应用 | 待澄清需求卡片、澄清记录 | 材料含多条诉求时拆分 | 字段完整度可度量，涉及应用有初判结果 |
| S2 | 需求确认 | 产品经理 | 待澄清需求 | 仅产品经理可确认；确认后编号不可更改 | 校验确认清单完整性，分配 REQ-项目号-流水号 | 需求池记录、需求确认单 | 不通过则退回并保留历史 | 编号唯一，确认人与时间可追溯 |
| S3 | 需求分析 | 产品经理 | 已入池需求、项目画像 | 会话必须绑定具体需求；右屏只读 | 按四段结构生成与更新内容，识别关联需求 | 分析版本、关联需求提示 | 需求未绑定时拒绝进入分析模式 | 四段结构齐全，关联提示可查看详情 |
| S4 | 说明书更新 | 系统 | 分析版本 | 一需求一份，可汇编 | 自动更新需求清单条目与说明书草稿 | 说明书草稿、清单更新 | 结构校验失败则阻断 | 可在线预览，内容与最新分析版本一致 |
| S5 | 原型生成与迭代 | 产品经理 | 分析版本 | 遵循设计规范；确认前不写入说明书 | 生成页面与状态，接收自然语言改稿 | 原型 HTML、页面清单 | 改稿引入死链或缺失状态则驳回 | 可交互预览，确认后写入说明书 |
| S6 | 评审 | 评审人 | 说明书在线预览、原型 | 评审结论必须留理由 | 记录意见，生成改进建议清单 | 评审记录、建议清单 | 建议未闭环不得进入开发 | 建议逐条可追踪、可关闭 |
| S7 | 改进闭环 | 产品经理 | 改进建议清单 | 每条建议需明确采纳或不采纳理由 | 会话式修改分析，说明书重新生成 | 新版本说明书、建议状态 | 评审人可重新打开已关闭建议 | 全部建议状态为已闭环 |
| S8 | 开发期变更 | 产品经理 | 变更诉求 | 按影响分级 | 评估影响范围，决定直接更新、重新评审或重新登记 | 变更记录、版本差异 | 重大变更未重评则阻断 | 变更分级有依据，受影响产物同步更新 |
| S9 | 状态跟进与规划 | 产品经理 / 研发 | 需求状态与迭代信息 | 只有评审通过的需求可排期 | 状态流转、风险预警、容量与依赖校验 | 看板、迭代计划、进展摘要 | 容量超限或依赖成环则阻断 | 状态与门禁一致，数字与看板一致 |

### 3.4 特别说明

| 项目 | 说明 |
| --- | --- |
| 信息接收方式 | 站内通知与邮件；触发时机为需求确认、评审发起、评审结论、建议闭环、状态变更与风险预警 |
| 审批条件与级数 | 需求确认由产品经理一级确认；评审结论由产品负责人签署；无多级行政审批 |
| 数据权限 | 按角色与资源归属控制；AI 执行以发起人身份运行，不放大权限；导出与分享链接可设有效期 |
| 交互与视觉体验 | 分析与原型采用左侧会话、右侧结构化预览；右屏只读，所有修改经由会话发起 |
